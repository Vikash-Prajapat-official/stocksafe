# Decisions

Where SPEC.md was unclear I chose the simplest option and wrote it here.

## Phase 1

1. **Spec file name.** The file was saved as `Spec.md`; renamed to `SPEC.md` to match the spec.
2. **Prisma 6, Tailwind 4, Zod 4.** Prisma 7 changes configuration and client generation; Prisma 6 is the stable, widely documented choice for this stack.
3. **Money and quantity are 32-bit `Int`.** Max about Rs 2.1 crore per price field and 2.1 billion units. Fine for a hospital store. `Grn.total_paise` could in theory exceed that for a very large invoice; revisit with `BigInt` if a real user hits it.
4. **Append-only ledger enforced in the database too.** Besides the rule in `stock.ts`, the first migration adds a trigger that rejects `UPDATE` and `DELETE` on `stock_movement`, and a `CHECK (quantity >= 0)` on `stock_balance`.
5. **Table names are snake_case** (`stock_movement`, `stock_balance`, ...) via `@@map`, matching the spec's field names; Prisma models stay PascalCase.
6. **Hospital is a single row.** One install = one hospital; `settings` is JSON.
7. **Indent direction.** `from_store_id` is the requesting ward, `to_store_id` is the supplying store (SPEC does not say).
8. **One image for app and worker.** The worker runs `tsx` from the same image with a different command. Bigger image than a standalone Next build, but one Dockerfile and no packaging surprises. The Postgres port is also published on 127.0.0.1:5434 only (5432 and 5433 are used by sibling apps; override with DB_PORT) for local tools.
9. **Backup service is Phase 5.** Phase 1 compose has app, worker, db only, as the phase list says.
10. **shadcn/ui.** `components.json` and the `cn` helper are in place; individual components are added as screens need them. `next-intl`, Auth.js, bcrypt, papaparse etc. are installed in the phase that first uses them.
11. **Health.** `GET /api/health` is public (needed by Docker healthcheck) and returns only ok/down; `/health` is a small page showing the same.

## Phase 2

1. **Auth.js v5 (next-auth@beta), JWT sessions, 12 hour expiry.** Credentials = phone + password, bcrypt cost 12. The JWT only carries the user id. On every API call and page the user is re-read from the database, so a deactivated user or a changed role takes effect immediately. Trade-off: JWTs cannot be revoked, so a password reset does not sign out existing sessions (deactivating the user does).
2. **Every API route is wrapped in `route(roles | "ANY", handler)`** (`src/lib/api.ts`). 401 = not signed in, 403 = wrong role. A unit test scans `src/app/api` and fails if any route (other than `/api/health` and `/api/auth/*`) is not wrapped, and checks 401/403 for every admin route and every role.
3. **Admin screens and APIs are ADMIN only**, including reading stores and suppliers. Later phases will add read-only lookups for the roles that need them (for example suppliers for the GRN screen).
4. **Items: GET is open to any signed-in user; create, edit and import are ADMIN only** (matches the spec's API table). Items are never deleted; use Active = off.
5. **Item identity = name + strength + form** (case and spacing ignored). Used for the 409 on create and for skipping duplicates on import. There is no database unique constraint on it, so two admins importing at the very same moment could create a duplicate; low risk, revisit if seen.
6. **Stock levels: 0 means "not set".** Rule when set: minimum <= reorder <= maximum. A file may give only a minimum.
7. **`unit` is what the store counts in** (tablet, vial, bottle, tube, piece), not the strength. If a file leaves it blank it defaults from the form.
8. **Import creates only.** Existing items are reported as "Already in the item list" and left alone. Valid rows are imported even when other rows fail; each failing row is listed with its row number, column and reason. A "Check file" dry run reports without importing. Limits: 5 MB, 5000 rows.
9. **SheetJS is installed from the SheetJS CDN tarball** (`xlsx@0.20.3`), because the npm registry copy (0.18.5) is old and has known vulnerabilities. This needs network access at `npm install` time only.
10. **NLEM seed is about 430 rows, not 300**: roughly 385 medicines plus about 45 common consumables (non-essential). I compiled it from memory of NLEM 2022 categories. **It has not been checked line by line against the official NLEM 2022 PDF.** Generic name is left blank (the name is already generic). Levels are all 0 until the admin sets them (demo levels come with the Phase 7 demo data). Seed also creates 3 stores, 3 suppliers and 5 demo users (phones 9000000001 to 9000000005, password from `SEED_PASSWORD`, default `ChangeMe@123`); it never overwrites an existing user.
11. **Login rate limit is in memory:** 5 failed attempts per phone and 30 per IP in 15 minutes. It resets when the app restarts. Fine for a single app container.
12. **Last-admin protection:** an admin cannot deactivate or demote themselves, and the last active admin cannot be removed.
13. **UI primitives are hand-written in shadcn/ui style** (Button, Input, Select) instead of using the shadcn CLI, so there is no network step. TanStack Table is not used yet: lists are server-paginated (50 per page). It will be added when a screen needs client-side sorting.
14. **Marketing landing page moved to `src/app/(marketing)/page.tsx`** (placeholder until Phase 6), matching the folder structure in the spec.

## Phase 3

1. **Issue vs transfer.** `issue` takes stock out of a store for consumption or department use (needs a reason) and writes ISSUE. `transfer` moves stock to another store or ward and writes TRANSFER_OUT and TRANSFER_IN together with one shared reference, so the ward then holds that stock. The Issue screen offers both.
2. **FEFO rules** (`src/lib/fefo.ts`). A batch is usable on its expiry date and expired from the next day (India date, IST). Ties on expiry take the smaller batch first, then the lower batch id, so results are repeatable. Expired and empty batches are never used.
3. **Choosing a batch by hand** (override) needs a reason of at least 3 characters, which is stored on the movement ("FEFO override: ..."). Expired batches are refused even with a reason. All other reasons only need to be non-empty.
4. **No overselling, three layers.** (a) Every operation takes a per-item advisory lock, so operations on the same item queue up and cannot deadlock each other. (b) The balance rows it reads are locked with `SELECT ... FOR UPDATE`. (c) The database `CHECK (quantity >= 0)`. A deadlock or write conflict that still happens is retried up to 5 times. I proved the tests catch missing locks by disabling (a) and (b): the multi-batch test failed and the opposing-transfer test deadlocked.
5. **Preview is advisory.** "Review FEFO split" reads without locking; "Confirm" recomputes under lock. If someone else took stock in between, the confirmed split can differ or fail with INSUFFICIENT_STOCK; nothing is ever half-applied.
6. **Receiving.** Batch numbers are compared ignoring case and extra spaces (stored upper case). The same batch number with a different expiry is refused (BATCH_MISMATCH). A later receipt of an existing batch keeps the first price and returns a warning. Already-expired stock cannot be received. Invoice totals must fit in 32-bit paise (about Rs 2.1 crore).
7. **Approvals.** Returns to supplier, expiry write-offs and adjustments need an active ADMIN as approver and a reason. For now the API routes are ADMIN only and the admin who does it is the approver; a request-then-approve workflow (someone else asks, the admin approves) arrives with the expiry centre in Phase 4. Write-off only works on an expired batch; damaged stock is an adjustment. `adjust` has no API route yet because the spec has none; stock count approval (Phase 4) will call it.
8. **Roles follow the spec table literally:** GRN = store keeper only; issue/transfer = store keeper and pharmacist; dispense = pharmacist only. An admin cannot receive or dispense (create a user with that role if one person does everything). Non-admins can only work in stores they are assigned to (`UserStore`); anyone signed in can read stock and the ledger.
9. **Not built:** RETURN_IN (a patient returning medicine) is in the data model but not in the `stock.ts` function list of the spec, so it is not implemented yet.
10. **Two schema additions:** `stock_movement.seq` (insertion order, so the bin card and its running balance are deterministic) and `item.gtin` (14-digit barcode number, optional, set on the item form or in the import file) so a scan can pick the item. Existing items simply have no barcode.
11. **Barcode scanning.** GS1 DataMatrix / GS1-128 codes are parsed for GTIN, expiry (AI 17, or best-before AI 15) and batch (AI 10); a plain EAN/UPC gives a GTIN only. A USB scanner works by typing into the scan box. The camera uses `@zxing/browser`, which browsers only allow on HTTPS or localhost; on plain `http://192.168...` the page says so and the USB or typed route still works. **Camera decoding has not been tested with a real camera** (the typed-code path and the parser are tested).
12. **Audit log** rows (GRN_CREATE, STOCK_ISSUE, STOCK_TRANSFER, STOCK_DISPENSE, STOCK_RETURN, STOCK_WRITEOFF, STOCK_ADJUST) are written inside the same transaction as the stock change.
13. **Bin card** shows newest first and a running balance per store and batch (not one balance across mixed stores).
14. **Dispensing slip** is the page itself printed with the browser's print function (everything else is hidden when printing). One slip per dispensing, with several items allowed.
15. **Integration tests need PostgreSQL.** `npm run test:integration` drops and recreates a database whose name must end in `_test` (default `stocksafe_test` on the compose database at port 5434), runs the migrations, then runs the tests. It refuses to touch any other name. `npm test` stays fast and needs no database.

## Phase 4

1. **Indent roles** (the spec lists "NURSE, STOREKEEPER" for the group, so I split it): a ward nurse raises and sends indents, only for her own ward; the store keeper of the supplying store approves, rejects, issues and closes. An admin or auditor can read every indent but not act; a pharmacist has no indent screen. A ward only sees its own indents, a store only sees the ones sent to it.
2. **Indent flow.** DRAFT, then SUBMITTED, then APPROVED, then ISSUED. Rejected ends it. "Approves partly" needed one new column (`qty_approved`): the store can approve less than requested, down to 0 for a line. PARTIAL means some approved quantity is still outstanding because stock ran short; the store can issue again later or **close** it (the remainder is dropped, with a note). A draft cannot be edited or deleted (the nurse sends it, or raises a new one). Every step is guarded in SQL, so two people acting at once cannot both succeed.
3. **Issuing an indent is a transfer** from the supplying store to the ward, FEFO, in one transaction with the indent update (`issueIndent` in `stock.ts`). The stock is in the ward's store immediately, so there is no separate "nurse confirms receipt" step. It issues what exists; if nothing at all can be issued the answer is 409 INSUFFICIENT_STOCK and the indent does not change. The ledger entries carry the indent as their reference.
4. **Expiry bands** come from `EXPIRY_ALERT_DAYS` (default 90,60,30, read as 30, 60, 90) and do not overlap: Expired, Within 30 days, 31 to 60, 61 to 90. A batch that expires today is "within 30 days"; expired means the day after. Values are quantity times cost price (paise).
5. **Expiry centre actions** replace the Phase 3 idea of a request-and-approve step: there is no request record in the data model, so an **admin** writes off (expired only) or returns to supplier directly and is recorded as the approver. A **store keeper or pharmacist** working in that store can **transfer** near-expiry stock to another store (a manual-batch transfer with an automatic reason). Expired stock cannot be transferred.
6. **Reorder rules** (`reorder.ts`). An item is low when usable on-hand is strictly below its reorder level (below its minimum when no reorder level is set); a level of 0 means not set, and items with no levels are never listed. Suggested order = maximum minus on-hand; if no maximum is set, order up to twice the reorder level. On-hand counts only non-expired stock, and expired quantity is shown beside it. Levels belong to the item, not to a store, so the default list is hospital-wide; picking one store compares that store's stock with the same levels (a small ward will look low).
7. **CSV export** of the reorder list is Excel-friendly (UTF-8 BOM, CRLF) and neutralises formula injection: a text cell starting with `=`, `+`, `-`, `@`, tab or CR is prefixed with a quote. The shared writer (`csv.ts`) will be reused for the reports in Phase 5. PDF is Phase 5.
8. **Dashboard** is hospital-wide and live: expired value, near-expiry value per band, items below reorder, stock-outs (items with a level set and nothing usable right now, not a history), indents waiting, counts in progress, the last 10 movements. It is also the landing page after sign-in now.
9. **Stock count design.**
   - The sheet snapshots every batch with stock in the store, plus batches stocked before that are not expired (their stock may be zero, but a count can find some). A completely unknown batch cannot be added to a count: receive it with a GRN.
   - The sheet is a **blind count** by default (system quantity hidden, tick a box to show it). Lines left blank are "not counted" and are never adjusted.
   - **Approval adjusts to the quantity counted minus the balance at the moment of approval**, not the snapshot, and records both in the reason. Lines whose stock moved during the count are flagged for the approver, who can send the count back for a recount. Best practice is to count when the store is quiet.
   - Only one count (OPEN or SUBMITTED) per store at a time, enforced by a database index. A store keeper counts only his stores; an admin can count any store; an auditor only reads.
   - Approval is ADMIN only and writes the ADJUSTMENT movements through `stock.ts` in one transaction; approving twice adjusts once. There is no rule that the approver must differ from the counter (a small hospital may have one admin); the audit log records both.
10. **Database safety nets:** the migration adds CHECK constraints (indent quantities: requested above 0, approved between 0 and requested, issued not above approved; count quantities not negative) and the one-active-count-per-store index. New columns: indent `seq`, `note`, `decision_note`, `updated_at`; indent line `qty_approved`; stock count `seq`, `created_at`, `submitted_at`, `approved_at`.
11. **Refactors:** `ApiError` moved to its own module (`api-error.ts`) so the workflow libraries do not pull in the sign-in code; `parseOptionalBody` lets an empty body mean "defaults" (approve everything as requested).
12. **Not built yet:** the stock-out days report and the other reports (Phase 5), draft editing for indents, scanning barcodes on the count sheet.

## Phase 5

1. **Patient labels moved out of the ledger (a deliberate change to the spec's data table).** SPEC puts `patient_label` on StockMovement and also says patient names must be anonymised after `RETENTION_DAYS`. Those two collide with the rule that a movement is never updated (a database trigger enforces it). So the label now lives in its own table, `movement_patient` (movement id, label, created at, anonymised at), and the retention job clears the label there. The ledger row is never touched, and a test proves the movements are byte-for-byte identical afterwards. The bin card shows "[anonymised]" for cleared labels. The migration copied any existing labels across before dropping the old column.
2. **Retention.** `RETENTION_DAYS` is read as 1 to 3650 days; anything else (empty, 0, text) falls back to 90, so names are never kept indefinitely by accident. The job runs every night at 02:00 India time, records each run in the audit log, and the dispensing screen tells the pharmacist the number of days.
3. **The audit log is append-only too** (a trigger refuses UPDATE, DELETE and TRUNCATE, like the ledger). The Audit log screen is read-only and open to ADMIN and AUDITOR, with filters (user, action, record type, dates) and a CSV download (up to 20,000 rows). Downloads of reports and of the log are themselves audited (`REPORT_EXPORT`).
4. **Reports** (ADMIN and AUDITOR only), as JSON, CSV or PDF: stock on hand, expiry, monthly consumption, ABC analysis, stock-out days. Definitions:
   - *Stock on hand:* usable (not expired) and expired quantity and value at cost, per item, one store or all.
   - *Monthly consumption:* issued + dispensed per item per month (India time), valued at the batch cost price. Transfers between stores are not consumption. Expiry write-offs are shown in their own column and are not in the value. Up to 24 months.
   - *ABC:* items ranked by consumption value; A while the items before it make up less than 80% of the total (so the item that crosses the line is still A), B up to 95%, C the rest. Integer maths in basis points. Items with no consumption are not listed.
   - *Stock-out days:* a day that ended with no usable (non-expired) stock, counted from the day the item was first stocked, rebuilt from the ledger history including expiry dates. Only items with at least one such day are listed. Up to 366 days. This is the one report that reads the ledger directly; the others read the SQL views `report_stock_on_hand` and `report_consumption`.
   - Limits: 300 rows on screen, 3,000 in a PDF (the CSV is always complete).
5. **CSV and PDF.** CSV is Excel-friendly (UTF-8 with BOM), money is exact rupees ("1500.00"), a text cell that could run as a formula is neutralised, and the totals are the last row. PDF uses Noto Sans (Latin and Devanagari files from `@fontsource/noto-sans-devanagari`, embedded) so Hindi item names print correctly; amounts are written "Rs 1,500.00" because the rupee sign is not in the Latin font file. A4, landscape when there are more than five columns, header repeated on every page, page numbers.
6. **Nightly jobs** (the `worker` container, India time, override with `ALERT_CRON` and `RETENTION_CRON`): retention at 02:00; alerts at 06:30 so the digest arrives before the day's work. The alert job works out the expiry and low-stock picture, writes `ALERT_JOB_RUN` to the audit log and, when email is set up, sends the digest. Email is optional: with no `SMTP_URL` or no valid `DIGEST_TO` the digest is skipped quietly. A mail failure is audited (`DIGEST_FAILED`) and never stops the job; there is no retry until the next morning. `npm run job:alerts` and `npm run job:retention` run a job once by hand. The digest text and HTML are built by a pure function; item names are HTML-escaped.
7. **Backups** (`backup` container). A first backup 45 seconds after the container starts, then nightly at `BACKUP_HOUR` (default 02:00 India time). Each backup is `pg_dump`, gzip, then AES-256-CBC with PBKDF2 (200,000 iterations) keyed by `BACKUP_PASSPHRASE`. Before it is kept it is decrypted and unzipped again as a check; a failed dump leaves no file; files older than `BACKUP_KEEP_DAYS` (default 14) are deleted. The container refuses to start, and compose refuses to start the stack, without a passphrase of at least 12 characters. **`restore.sh` only restores into a NEW database** and refuses an existing name, so a mistake cannot overwrite live data. I tested a real restore against the live data (identical counts, patient rows, audit rows, views and triggers) as well as the wrong-passphrase, failed-dump and pruning cases. Backups sit on the same machine and disk as the database: copy the backup folder somewhere else regularly (a USB drive or another PC). The app mounts the backup volume read-only so the System page can show the latest backup.
8. **System page** (admin only): latest backup and age, email set-up, recipients (count only), last digest and failure, last alert and retention runs, retention days, expiry bands. Nothing can be changed there; settings stay in `.env`.
9. **`.gitattributes`** keeps the backup scripts on Unix line endings, so a clone made on Windows does not break the container.
10. **Not built:** an audit-log PDF, charts, digest retries, automatic off-site upload of backups, and a restore screen (restore is a command, documented in ADMIN_GUIDE.md in Phase 7).
